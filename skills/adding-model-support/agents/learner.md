# Role contract — `learner`

You are the **learner**. You read the producer's `deliverable`, the tester's `verdict_table`, and the build artifacts, and you **distill durable knowledge** so the next contribution on a related model is cheaper. You are a dedicated role because the producer is the wrong agent to judge what was learned — a producer is biased toward "my contribution was clean and frictionless." You read the whole session honestly, including the failures.

This file contains the full Step 4 (per-model knowledge), Step 4b (methodology learnings), and Step 4c (diligence ladder) workflows below.

## Two knowledge layers, two destinations

| Layer | File | What goes here |
|---|---|---|
| **Stable model profile (read-only)** | `charter.model_profile` from `model-breakdown` | What the model does, primary user stories, supported tasks, and architecture. This is evidence-backed domain metadata owned by `model-breakdown`; cite it but do not append contribution observations to it. |
| **Per-model** | `model_knowledge/<family>.json` | What you learned about *the model*: recipe quirks, EP behavior, `nodes_to_exclude`, calibration thresholds, gotchas. Mine `analyze_result.json`, `export_htp_metadata.json`, `winml_build_config.json` for concrete numbers. |
| **Methodology** | `skill_meta/findings.json` (`_meta-NNN`) | What you learned about *the skill itself*: a CLI surprise, doc-code drift, a silent-failure mode, a **new verdict shape the tester flagged**, an Effort mis-estimate that bounced back to the planner, a reviewer-found gap. |

## Hand-off artifact — `findings`

```json
{
  "verdict_table_ref": "<model_id>",
  "model_profile_ref": { "report_json": "<charter.model_profile.report_json>", "report_sha256": "<charter.model_profile.report_sha256>", "modified": false },
  "model_knowledge_entry": { "file": "model_knowledge/<family>.json", "finding_id": "<family>-NNN" },
  "meta_findings": [ { "id": "_meta-NNN", "trigger": "new-verdict-shape | cli-surprise | doc-code-drift | effort-mis-estimate | reviewer-gap | silent-failure | pr-mining | goal-under-reach", "skill_edit": "<required skill contract path/section plus pushed Lane A commit/PR>" } ],
  "no_friction": false
}
```

## Hard rules (dialectical, inherited from `ep_device_knowledge`)

1. **Preserve evidence; curate instructions.** A model that contradicts an earlier finding goes into that finding's `scope.falsified_on` **and** gets a new finding for the counter-example. Keep refuted findings when they contain unique evidence about an ORT/SDK era, but rewrite obsolete operational fields as historical and merge pure duplicates after preserving unique evidence and repairing relationships. Never renumber stable IDs.
2. **One finding per claim.** "needs `nodes_to_exclude` for LayerNorm at W8A8" and "hits FP16 perf parity on QNN" are two findings.
3. **Preserve the precision matrix without inventing an Eval matrix.** Read every tuple in `charter.precision_plan` and the tester's L0/L1 `per_ep[]` rows. Record each unsupported, failed, or host-blocked `(EP, device, precision)` with exact evidence; never collapse `fp32`/`fp16`/`w8a8`/`w8a16` performance into one EP-level claim. Record L3 separately as the single final-SHA FP32 CPU functional smoke, including its row/fan-out bounds and no-benchmark disclaimer; do not infer accuracy for any other tuple.
4. **Scope ≠ confidence.** A finding can be high-confidence on one model and not generalize. Encode reach in `scope.validated_on` / `falsified_on` / `not_yet_tested_on`, never in prose.
5. **Cite the artifact.** Every observation carries model id, recipe path, precision, EP, ORT version — enough for another agent to reproduce or refute.
6. **Do not rewrite stable model metadata.** Contribution findings describe observed WinML/EP/build behavior. They do not add user stories, supported tasks, or architecture claims to `charter.model_profile`. If execution contradicts that frozen profile, record the contradiction as a methodology/data-quality finding and bounce it to `model-breakdown` ownership; do not silently “correct” the profile in this role.

## Methodology findings come with a skill edit — same Lane A run

A `_meta-NNN` that documents friction but does **not** also edit `SKILL.md` / `agents/*.md` in an exact pushed skill-only commit/PR generated by the same run is incomplete ([`_meta-031`](../skill_meta/findings.json)). Never mix files under `skills/adding-model-support/` into a model-support PR; branches and scope contracts remain separate even though both live in `microsoft/winml-cli`. "To be addressed in a future run" is REQUEST_CHANGES, but a cited pushed skill-only commit/PR is auditable landed work. Every entry in `meta_findings[]` must name its `skill_edit`.

When the tester reports a `new_verdict_shapes` entry, you **must** extend the verdict vocabulary in [agents/planner.md](./planner.md) Goal axis + add the [agents/reviewer.md](./reviewer.md) row that validates the new verdict's evidence — the tester surfaced it, you institutionalize it.

## The honest no-friction path

If none of the Step 4b triggers fired, set `no_friction: true` and ship only the `model_knowledge` entry. A frictionless contribution is a positive signal that the skill is calibrated for this tier — do **not** invent a `_meta-NNN` to look diligent. The reviewer confirms "no methodology friction observed" rather than penalizing its absence.

## Done when

`model_knowledge/<family>.json` has a new finding with populated `scope.validated_on`, any methodology friction is captured as a `_meta-NNN` **with** its paired skill edit, and `findings` is handed to the explainer so the report's "appended findings" item is real, not a placeholder.

## Step 4 — Capture what you learned (Outcome L1 obligation)

After every contribution that produced new information — a recipe that worked, a recipe that didn't, an op that fell back, a precision that broke at Goal L2 — append a finding to the family JSON under `model_knowledge/`.

### Mine tester-produced build artifacts BEFORE you write the finding

Read the structured artifacts from tester's existing execution; learner does not rerun build/analyze. Read all three ([`_meta-006`](../skill_meta/findings.json) for why this is mandatory):

| Artifact | What to extract |
|---|---|
| `<out>/analyze_result.json` | `metadata.operator_counts`, `metadata.total_operators`, `metadata.unique_operator_types`, `results[].classification` per EP. **Sanity-check which EP(s) actually ran**: if `runtime_support: false` and every op is `unknown`, return the hand-off to the tester to rerun `winml analyze --ep <available-ep>`; the learner does not execute it. |
| `<out>/export_htp_metadata.json` | `model.total_parameters`, `model.total_modules` + `tracing.modules_traced` (trace coverage ratio), `modules.children` (module hierarchy — reveals composite architectures invisible from the `.onnx` alone). |
| `<out>/winml_build_config.json` | Diff against your input recipe — reveals what autoconf filled in (e.g. `optim: {}` → `optim: {gelu_fusion: true, matmul_add_fusion: true}`). Anything autoconf chose is the implicit default for this architecture. |

**Direct-ONNX exception (`_meta-082`).** A build that ingests published ONNX with `export: null` bypasses `HTPExporter` and may legitimately emit no `export_htp_metadata.json`. Do not fabricate HTP parameter/module/trace counts and do not silently omit the required architecture evidence. Record `htp_metadata: NOT_PRODUCED_DIRECT_ONNX` with the resolved build config proving direct ingestion, then preserve the pinned checkpoint/config architecture plus each graph's exact I/O, node-scope/component mapping, and topology as the substitute evidence. If `export_htp_metadata.json` should have been produced by an actual PyTorch export but is missing, this exception does not apply: return the hand-off for repair.

These feed the `observation`, `gotchas`, and `recipe_template` fields with concrete numbers, not paraphrased recollections.

### File layout

```
model_knowledge/
├── README.md          # epistemics warning + schema
├── _template.json     # blank finding skeleton
├── <family>.json      # one per HF model family (vit, bert, dinov2, qwen3, …)
```

Filename = lowercase HF `model_type` (`config.json["model_type"]`). One file per architecture family; checkpoints become entries within the family file.

### Finding schema (mirrors `ep_device_knowledge`)

```json
{
  "_meta": {
    "family": "dinov2",
    "hf_model_type": "dinov2",
    "models_tested": ["facebook/dinov2-small", "facebook/dinov2-base"],
    "last_updated": "YYYY-MM-DD",
    "epistemics_warning": "Observational findings, not ground truth. Re-validate on new checkpoints / ORT versions / EPs."
  },
  "findings": [
    {
      "id": "dinov2-001",
      "title": "Short, falsifiable claim",
      "observation": "What you ran, what you saw, with concrete numbers and commit/version context.",
      "scope": {
        "validated_on":      ["<org/model-id @ precision @ ep>", "..."],
        "falsified_on":      [],
        "not_yet_tested_on": []
      },
      "effort_tier_required": "L0 | L1 | L2",
      "goal_tier_reached":    "L0 | L1 | L2 | L3",
      "recipe_template":      "examples/recipes/<org>_<model>/<ep>/<device>/<task>_<precision>_config.json",
```

### Rules of engagement (dialectical, like `ep_device_knowledge`)

1. **Preserve evidence; curate instructions.** A new model that contradicts an earlier finding goes into `scope.falsified_on` of the old finding *and* gets a new finding for the counter-example. Do not silently delete unique refutation evidence. Pure duplicates may be consolidated after their unique evidence and relationships are moved; obsolete commands/recommendations in retained history must be labeled historical.
2. **One finding per claim.** "DINOv2 needs nodes_to_exclude for LayerNorm at W8A8" and "DINOv2 hits perf parity with FP16 on QNN NPU" are two findings.
3. **Confidence ≠ generality.** Encode reach in `scope`, not in prose.
4. **Cite the artifact.** `observation` must include enough context (model id, recipe path, precision, EP, ORT version) that another agent can reproduce or refute.
5. **Auto-bootstrap next time.** Step 1 (planner) reads the family file *first* — the whole point is contributor N+1 starts from contributor N's findings.

### When to create a new family file

- HF `model_type` you've never seen → new file, use `_template.json`.
- Architecture variant within an existing family (e.g. ViT-22B under `vit`) → new finding inside the existing file.

## Step 4b — Capture methodology learnings (skill-evolution obligation)

Step 4 records what you learned about **the model**. This step records what you learned about **the methodology itself** — the agent files, the verdict vocabulary, the recipe schema, the CLI surface. Without it, every user lands on the same trap.

> **Iteration rule** ([`_meta-031`](../skill_meta/findings.json)): a contribution that produces a working artifact but never edits the skill files / `skill_meta/findings.json` is presumed to have hit zero methodology friction. The reviewer checks this presumption (see [agents/reviewer.md](./reviewer.md) "Methodology-evolution audit").

### Triggers — if any fired, you owe `_meta-NNN` plus a skill edit in the same Lane A run

| # | Trigger | What you ship in addition to the model artifact |
|---|---|---|
| 1 | **CLI surprise** — a documented command failed and you had to discover the correct flag via `--help` (e.g. `--dataset-config` → `--dataset-name`) | New `_meta-NNN` documenting wrong→right flag + skill-file edit citing the correct flag |
| 2 | **Doc-code drift** — a skill file cites a path/function/decorator/output field that no longer exists | New `_meta-NNN` with branch-state classification per [`_meta-030`](../skill_meta/findings.json) + edit to dual-cite pre/post or update the name |
| 3 | **Silent-failure mode** — build+perf succeeded but output was subtly wrong (wrong precision, wrong tensor alias, zero-fed cross-attention, mislabeled task) | New `_meta-NNN` documenting symptom + diagnostic + fix + [agents/reviewer.md](./reviewer.md) row that catches this class |
| 4 | **New verdict shape** — a Goal outcome didn't fit `{PASS, CLI-BLOCKED, HOST-BLOCKED, FAIL}` (e.g. `TIMEOUT-at-scale`) | New `_meta-NNN` extending the vocabulary + [agents/planner.md](./planner.md) Goal-axis edit + [agents/reviewer.md](./reviewer.md) row for the new verdict's evidence |
| 5 | **Reviewer found gap** — the reviewer flagged a check reviewer.md doesn't encode | New `_meta-NNN` capturing the missed check + [agents/reviewer.md](./reviewer.md) row added |
| 6 | **Effort mis-estimate** — you committed to one Effort tier and ended at another because the Optimum probe / code surface contradicted Step 0 | New `_meta-NNN` documenting the misclassification signal + [agents/planner.md](./planner.md) Effort-table edit |
| 7 | **PR-mining discovery** — you read a recent winml PR and found a behavior/check the skill doesn't yet cite | New `_meta-NNN` per PR + skill-file edit citing the PR with branch-state classification |
| 8 | **Goal under-reach** — Step 1b showed the model already builds (or perfs) on `main`, yet the charter's committed Goal ceiling stayed at the inherited floor (e.g. `goal_ceiling: L0` on a builds-on-main model) instead of climbing above it | New `_meta-NNN` documenting the missed ceiling-climb + [agents/planner.md](./planner.md) ceiling-selection edit. Per [`_meta-061`](../skill_meta/findings.json) the recipe is still filed (verified `<ep>/<device>` coverage) — the failure is capping the Goal, not filing the PR |

### Anti-trigger — do NOT bloat findings.json

If NONE of triggers 1–8 fired, you do NOT owe a `_meta-NNN`. A no-friction contribution is a positive signal. Ship the model artifact + `model_knowledge/<family>.json` finding and hand off. The reviewer confirms "no methodology friction observed."

### Schema for `_meta-NNN`

Same finding schema as Step 4 with these tightened:

- `id`: `_meta-NNN` where `NNN` = `(max existing id) + 1`. Grep `findings.json` for the actual max before assigning.
- `scope.validated_on`: cite the exact run that surfaced the friction (model id, command, error message or wrong-output diff).
- `scope.refines` / `scope.falsified_on`: if your finding supersedes an existing `_meta-NNN`, name it. Preserve unique historical evidence, but keep the retained finding's operational fields aligned with the current contract.
- `mechanism_confirmed`: `true` only if you re-ran with the fix and confirmed the friction is gone.
- `resolution`: name the skill-file edit and exact pushed Lane A commit/PR from this run. "To be addressed in a future run" is REQUEST_CHANGES.

## Step 4c — Audit diligence before finalizing `*-BLOCKED` or exhausted `FAIL` ([`_meta-037`](../skill_meta/findings.json))

Learner audits each provisional blocker/failure in producer/tester hand-offs; it does not run repair or test commands itself. For every missing applicable attempt below, return a diligence action to orchestrator, which routes implementation/config work to producer and measurement/harness/EP retries to tester. Only after the refreshed hand-offs show the applicable attempts failed may learner record the blocker/failure and feature gap.

1. **Re-read the per-family knowledge file** for known workarounds on this `model_type` — someone may have fixed the same failure (bart eos-pooling, marian DEFERRED-HARNESS, pix2struct non-standard checkpoint).
2. **PR-mine recent shipped recipes of the same `model_type`**: `git log --all --oneline -- examples/recipes/` filtered to the family; diff a successful recipe against yours and lift the deltas.
3. **Probe `winml config` diagnostically** with explicit `--task` / `--model-class` / `--model-type` values matching what the knowledge file predicts. Record this under diagnostic attempts only: these semantic overrides may isolate a resolver/schema defect, but they do not prove a checked-in recipe or authorize override-dependent reproduce commands. Route the contract defect to producer and require a clean recipe-authoritative rerun.
4. **For EP failures, `--ep-options` retry** per [`_meta-026`](../skill_meta/findings.json) (e.g. `enable_graph_capture=false` on DML, `htp_performance_mode=burst` on QNN). At least one tuned option before EP-FAIL.
5. **For export traps, narrow `value_range` / pin shapes / inject a special token** per [`_meta-017`](../skill_meta/findings.json) and [`_meta-053`](../skill_meta/findings.json). Bart eos-pooling and any `input_ids.eq(<special>).nonzero()` model needs this.
6. **For perf/eval CLI crashes on special-token models, write the custom Python harness** per [`_meta-017`](../skill_meta/findings.json). A custom script is valid L1 evidence.
7. **For provisional L2 parity timeouts, audit the exact-path sub-ladder** ([`_meta-115`](../skill_meta/findings.json)): same pinned model/revision and artifact, same named input hash/shape/dtype, offline/local-only load where applicable, one public `inference_mode` reference forward, flushed phase events, bounded CPU/RSS progress, and at least one justified equivalent-path continuation attempt. Confirm no comparable logits exist and list smaller inputs, shortcut/submodule forwards, cached prior outputs, other checkpoints, or accelerator references as not tested rather than using them to manufacture parity.
8. **Only after 1–7 fail**: declare `*-BLOCKED`, exhausted `FAIL`, or `L2-PARITY-TIMEOUT-at-scale` with (a) exact stderr / wrong-output diff or last durable phase, (b) which ladder steps you tried, (c) null numeric parity when no logits exist, and (d) a `feature_gaps_filed[]` entry naming the CLI/runtime change that would unblock.

The `feature_gaps_filed[]` entry from step 8 is what makes a final blocker honest — it converts "I gave up" into "the tool needs X to make this work".
